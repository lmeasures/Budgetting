# ADR-007: Data Synchronization Strategy

## Status
Proposed

## Context
Users require the ability to sync local client data (stored in RxDB/IndexedDB) with MongoDB Atlas cloud storage. A synchronization strategy must be defined that handles:
- Offline-first operation (application functions without cloud connectivity)
- Conflict resolution when data changes occur on both client and server
- Data consistency across devices/sessions
- Encryption during transit and at rest
- Partial sync failures and recovery

## Decision

### Sync Architecture: Offline-First with Event-Driven Sync

We will implement a **hybrid offline-first approach** with the following characteristics:

#### 1. Sync Direction & Frequency
- **Local-first**: All mutations occur on local RxDB instance immediately
- **Async background sync**: Changes are queued and synced to MongoDB Atlas when connectivity is available
- **Sync triggers**:
  - On-demand (user initiates manual sync)
  - Automatic on connection restore
  - Periodic background sync (every 5 minutes when connected)

#### 2. Conflict Resolution Strategy
Use **Last-Write-Wins (LWW)** with client-side timestamps for conflict resolution:

```
Client Operation Priority:
1. Timestamp comparison (server vs client)
2. Operation type priority (Deletes < Updates < Inserts, with deletions winning)
3. Client ID tie-breaker (deterministic resolution)
```

**Implementation**:
- Each document maintains `_clientUpdatedAt`, `_serverUpdatedAt`, `_clientId`, `_syncState` fields
- On sync conflict, compare `_clientUpdatedAt` vs `_serverUpdatedAt`
- Merge strategy: field-level merging for complex objects (not full document replacement)

#### 3. Data Encryption in Transit
- All API requests use **HTTPS/TLS 1.3**
- Request payload encrypted with MongoDB's **Client-Side Field Level Encryption (CSFLE)** before transmission
- Encryption keys derived from user passphrase (Argon2-derived key) as per ADR-006
- Server stores encrypted data; cannot decrypt without client key

#### 4. Sync State Management
Track sync status with document-level state:

```
_syncState: 'synced' | 'pending' | 'failed' | 'conflicted'
_syncError: null | { code: string, message: string, retry: boolean }
_syncRetries: number
```

Failed syncs automatically retry with exponential backoff (1s, 2s, 4s, 8s, 30s max).

#### 5. Selective Sync
Users can configure:
- **Sync enabled/disabled** (global toggle)
- **Sync scope** (which collections or budget items)
- **Sync frequency** (on-demand only, periodic, or always)

#### 6. Detecting Stale Data
- Client checks `_serverUpdatedAt` against local cache
- If local data is older than server by > 24 hours without sync, warn user
- On first sync after app wake, validate local data hasn't diverged significantly

### Sync Endpoints

```
POST /api/v1/sync/upload
POST /api/v1/sync/download
POST /api/v1/sync/changes
GET  /api/v1/sync/status
```

Details in ADR-009 (API Specification).

## Alternatives

1. **Cloud-First (Server Source of Truth)**
   - Requires always-online; poor UX on poor connectivity
   - Rejected: violates offline-first requirement

2. **Operational Transformation (OT)**
   - Complex to implement; better for collaborative editing (not needed here)
   - Rejected: over-engineered for single-user use case

3. **Conflict-Free Replicated Data Type (CRDT)**
   - Mathematically sound but memory-intensive
   - Rejected: complexity outweighs benefit for non-collaborative scenarios

## Consequences

✅ **Positive**:
- Application functions seamlessly offline
- User data never lost due to connectivity
- Graceful degradation on poor networks
- Field-level merge prevents total document loss on conflicts

⚠️ **Negative**:
- Added complexity in sync logic and error handling
- Timestamp skew between client/server must be managed
- User education needed on "pending" state and sync status
- Potential stale data visibility if user doesn't explicitly sync
- Higher storage overhead (tracking sync metadata)

🔧 **Mitigations**:
- Implement robust testing for all sync edge cases
- Clear UI indicators of sync status and conflicts
- Automatic retry mechanism with user-visible status
- Admin dashboard to monitor sync issues across users
